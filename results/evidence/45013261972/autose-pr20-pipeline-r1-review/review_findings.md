The crash is gone, but the fix does the opposite of what the issue asks. Without codehilite, codehilite-only options (linenums, guess_lang, noclasses) are now written onto <code> as attributes, where the issue says they should be ignored and the block rendered as if they were absent. The new tests assert that wrong output, and the changelog documents it.

- [blocker] markdown/extensions/fenced_code.py:161 Codehilite-only options are emitted as HTML attributes when codehilite is disabled, instead of being ignored. The patch only changes how None/True values are stringified, so linenums, guess_lang and noclasses still reach the <code> element. — evidence: Actual for '``` { .python linenums }' with extensions=['fenced_code','attr_list']: '<pre><code class="language-python" linenums="True">print(1)\n</code></pre>'. Expected per issue (block rendered as if options were not written): '<pre><code class="language-python">print(1)\n</code></pre>'. Same leak for '{ .python linenums="1" guess_lang noclasses }', which gives linenums="True" guess_lang="True" noclasses="True" (issue expects none of these). The fix needs to drop codehilite-only keys in the non-highlighting branch, by key name and not by value type, because linenums="1" is a string and must also be dropped. Attributes such as data-x must still be kept.
- [major] tests/test_syntax/extensions/test_fenced_code_bool_options.py:63 The new tests lock in the incorrect behaviour. They assert linenums="True" on <code>, the opposite of the issue's expected output, so they would pass with the bug and fail with a correct fix. — evidence: Lines 63-75 expect '<pre><code class="language-python" linenums="True">print(1)\n</code></pre>' for both '{ .python linenums }' and '{ .python linenums=true }'. The issue expects '<pre><code class="language-python">print(1)\n</code></pre>'. No test covers guess_lang, noclasses, linenums="1" or linenums=false, all of which the issue lists.
