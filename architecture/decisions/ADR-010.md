# ADR-010: Triggers, authorization and concurrency

- **Status:** Accepted, amended by ADR-014 (2026-11-22: review-only runs execute trusted AutoSE code and only accept PRs from the fork's own branches)
- **Date:** 2026-11-22
- **Assignment decision:** D10 (triggers)
- **Decided by:** MittalManas2005, choosing from the options in `architecture/decision_briefs.md` (prepared with AI assistance)

## Context
A maintainer starts AutoSE by labelling an issue or posting a comment. On a public repository anyone can comment, so the comment trigger needs an authorization check.

Stage 5 needs upstream CI to run on the bot's PR. PRs opened with `GITHUB_TOKEN` get CI runs in an approval-required state, and events created with `GITHUB_TOKEN` don't start other workflows (except `workflow_dispatch` and `repository_dispatch`).

Two runs for the same issue (e.g. a label and a comment close together) must not corrupt each other.

## Decision
**Triggers** (`.github/workflows/autose.yml`):

| Event | Condition | Mode |
|---|---|---|
| `issues: labeled` | label name is `autose` | `full` |
| `issue_comment: created` on an issue | body starts with `/autose`; author is not a bot | `full`, or `resume` if a stopped run (NEEDS_INPUT) exists; the comment text is passed to the A1 skill's update mode as the maintainer's answer |
| `issue_comment: created` on a PR | body starts with `/autose`; author is not a bot | `review-only` for the PR's latest commit (also used for the seeded reviewer-check PRs) |
| `workflow_dispatch` | inputs: issue or PR number, mode, variant (`pipeline` / `single`), reviewer model | development and experiments |

**Who may start a run:** the gate job checks the sender's permission on the repository through the API (`admin`, `maintain` or `write`), and for comments also `author_association` ∈ {OWNER, MEMBER, COLLABORATOR}. Anyone else is ignored, with a short reply. Only users with triage access can add labels in the first place.

**CI on the bot's PR:** the PR is opened by the AutoSE GitHub App (ADR-008). Its events trigger the fork's existing upstream workflows (`tox.yml`, `changelog-enforcer`, …) normally, so stage 5 checks real CI without modifying upstream files.

**Concurrency:**
- `concurrency: group: autose-issue-<number>`, with `cancel-in-progress: false`. A second run for the same issue waits instead of interleaving; GitHub keeps one pending run per group.
- Different issues run in parallel.
- Branch names (`autose/issue-<N>`) and artifact names include the issue number, and artifact names also include the run round.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| Any commenter can trigger | Anyone could spend the plan's usage or attempt injection with a fresh run. |
| `cancel-in-progress: true` | A newer trigger would kill a run mid-release, possibly leaving a half-updated PR. |
| Trigger CI by adding `workflow_dispatch` to upstream's CI | Works with `GITHUB_TOKEN`, but modifies the target repository's CI and loses the normal PR check view. |
| `pull_request_target` or `push` triggers | Not needed. `pull_request_target` is a known risk for running untrusted code with secrets. |

## Consequences
**Positive**
- Only maintainers can spend usage or start changes.
- Runs per issue are serialized.
- Real upstream CI gates stage 5.

**Negative / risks**
- `issues` and `issue_comment` workflows always run the workflow file from the default branch. Workflow changes must be merged to `main` before they can be tested with those triggers; `workflow_dispatch` is used during development.
- GitHub keeps only one pending run per group: a third trigger replaces the second pending one, by design.

## Evaluation
Trigger from an unauthorized account, or with a bot comment: no run, or an immediate stop at the gate. Trigger twice quickly: the second run is queued, not interleaved. Both are recorded in `results/runs.md`.
