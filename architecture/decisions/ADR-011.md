# ADR-011: Requirements stage reuses the adapted A1 skill, with a PASS / NEEDS_INPUT / FAIL gate

- **Status:** Accepted
- **Date:** 2026-11-22
- **Assignment decision:** stage 1 design (the assignment asks to reuse the A1 skill)
- **Decided by:** MittalManas2005 (policy chosen during Phase 2; skill adapted in place, see `a1_skill.md` §12 and the git history)

## Context
Stage 1 must write a spec with acceptance criteria, and its check is "all acceptance criteria are testable".

The A1 skill (`requirements-spec-builder` v1.2) was built for interactive requirements work:
- web evidence through MCP fetch;
- three output files;
- a readiness rule where an item is Ready only if every acceptance criterion is confirmed by a stakeholder quote.

Applied unchanged to GitHub issues, almost every real issue would stop at stage 1, and web access in a job that reads untrusted text is a security risk (ADR-009). One of the five evaluation issues is deliberately vague.

## Decision
- **Reuse the A1 skill, adapted in place** to v1.3-autose.
- **What changed:**
  - input is one issue plus a read-only repository;
  - evidence comes from the repository only, with no network;
  - new rule R9 (read-only, offline, no execution);
  - acceptance criteria must be testable through the public interface, with a named oracle kind and preservation ACs;
  - output is one `spec.md` with machine-readable front matter.
- **What stays from A1:** rules R1–R8, the Confirmed/Inferred/Open labels, the IDs, the 8-step workflow, validation checks V1–V6, and update mode.
- **Stage gate (skill §8.5):**
  - **PASS:** every acceptance criterion is testable and no P1 question is open. `[Inferred]` criteria may proceed but are listed for the maintainer to confirm on the PR.
  - **NEEDS_INPUT:** a P1 question has no safe default. The orchestrator posts the questions on the issue and stops; the maintainer's `/autose` reply re-runs the skill in update mode (ADR-004, ADR-010).
  - **FAIL:** no testable acceptance criterion can be written. The reason is recorded and the run stops.
- **The skill file is bundled** in the fork at `autose/skills/requirements-spec-builder.md`, as a copy of `autose-a3/a1_skill.md`, kept in sync the same way as `ARCHITECTURE.md` (ADR-003).
- **Experiment protocol:** maintainer answers are scripted (`experiment/issues/issue_5_maintainer_answer.md`, `maintainer_answer_generic.md`) and posted verbatim, so every run and variant gets the same input.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| Keep A1's strict readiness rule (stop unless every criterion is Confirmed) | Most realistic issues would never reach a PR. |
| Always proceed, turning questions into assumptions | The vague issue would never exercise clarification. Wrong assumptions would surface only at review. |
| Write a new, short requirements prompt | Would not reuse the A1 skill as the assignment requires, and would lose its traceability rules. |

## Consequences
**Positive**
- The A1 work is reused visibly (v1.2 and v1.3 are both in git history).
- Stage 1 has a precise, machine-checkable gate.
- The vague issue has a defined path (questions → answer → update mode).

**Negative / risks**
- The skill is long, and Haiku may follow it less faithfully (ADR-006). This shows up in the stage-1 pass rate.
- Scripted answers make experiments repeatable but less realistic than live answers.

## Evaluation
Stage-1 results per issue are reported in `results/results.csv`: status, number of acceptance criteria, number of Inferred criteria, P1 questions. For issue 5 we check that NEEDS_INPUT occurs and that update mode then reaches PASS.
