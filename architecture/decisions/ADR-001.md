# ADR-001: Five LLM roles and a deterministic release step

- **Status:** Accepted. Confirmed by experiment E1 (2026-11-22, see "Evaluation result" below).
- **Date:** 2026-11-22
- **Assignment decision:** D1 (splitting the work)
- **Decided by:** MittalManas2005, choosing from the options in `architecture/decision_briefs.md` (prepared with AI assistance)

## Context
AutoSE must carry out six fixed stages: requirements, design, implementation, testing, release, review. Each stage must pass its check before handing over, and the reviewer must be independent of the other agents.

The work mixes judgement-heavy steps (interpreting an issue, planning against the architecture, writing code, writing tests, reviewing) with purely mechanical steps (pushing a branch, opening a PR, waiting for CI).

Two sources informed the choice:
- **The course pattern catalogue** (`karthikv1392/autose-agent-patterns`) warns that "a passing critique does not guarantee passing tests". Its demos are judged "by executing tests, not by an LLM's opinion".
- **Anthropic's harness study** reports that "separating the agent doing the work from the agent judging it proves to be a strong lever", and that "every component in a harness encodes an assumption about what the model can't do on its own".

## Decision
Use **five LLM roles** plus **one deterministic release step**:

| Stage | Handled by |
|---|---|
| 1 Requirements | Requirements agent (applies the adapted A1 skill; ADR-011) |
| 2 Design | Design agent |
| 3 Implementation | Implementer agent |
| 4 Testing | Tester agent writes acceptance tests; a deterministic runner executes the full suite |
| 5 Release | Release job: plain code, no LLM |
| 6 Review | Reviewer agent in its own job (ADR-008) |

Each role is a separate, short-lived `claude -p` session with its own prompt, model settings and tool permissions (ADR-005, ADR-006).

The design contains two **generator–critic loops** (catalogue pattern M6; Anthropic's evaluator-optimizer):
- the Implementer is checked by the Tester and by real test execution;
- the whole change is checked by the independent Reviewer.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| One agent for all stages | One growing context, the agent grades its own work, and one tool set for everything. Kept as **experiment E1** (as a Self-Reflection agent) so the decision is tested, not assumed. |
| One LLM agent per stage, including Release | Release needs no judgement. An LLM holding push rights is an unnecessary prompt-injection risk. |
| Implementer also writes its own tests (4 roles) | The tests would encode the implementer's own reading of the spec, so a misunderstanding would pass its own tests. |
| Debate, Voting or Sub-agent spawning as the main structure | Debate and Voting multiply cost per stage. Sub-agent spawning suits large multi-module refactors, not 1–3 file issues. Swarm conflicts with ADR-002 (code decides transitions). |

## Consequences
**Positive**
- Each role gets only the context and tools it needs (least privilege, smaller prompts).
- Verification is done by agents that did not produce the work.
- The privileged step has no LLM in it.

**Negative / risks**
- More hand-offs to specify (ADR-003). Information can be lost between roles.
- More calls per run than a single agent; the token cost is measured, not assumed.
- Five prompts to maintain.

## Evaluation
**Experiment E1** (`experiment/variants.md`): the role pipeline against a single Self-Reflection agent doing stages 1–4, with identical checks, Release and Reviewer. Measured on the 5 issues:
- pass rate per stage;
- hidden-test pass rate;
- reviewer findings;
- tokens and wall-clock time.

If the single agent matches the pipeline's quality at clearly lower cost, this ADR is superseded.

## Evaluation result: experiment E1 (2026-11-22)
Same code (fork `main` `ca2d6d3`), same five issues, same reviewer (Sonnet). Baseline attempt 2 used the `pipeline` variant; E1 used the `single` variant (one Self-Reflection agent for stages 1–4). Run links and per-run data are in `results/runs.md` and `results/results.csv`.

| Measure | `pipeline` | `single` |
|---|---|---|
| Hidden tests passed | 17/18 | 17/18 (the same test missed on #7) |
| Runs approved in round 1 | 5/5 | 4/5 |
| Output tokens | 273,496 | 154,041 (−44%) |
| All tokens (input, cached and output) | 9.06 M | 8.51 M (−6%) |
| List-price equivalent | $0.78 | $0.74 (−5%) |
| Deterministic checks failed (and retried) | 1 | 4 |
| Behaviour on the vague issue #7 | stopped and asked the maintainer | did not ask; guessed |
| Reviewer findings | 5 minor | 1 major (a leftover debugging file only the reviewer caught), 1 minor |

**Decision (MittalManas2005): ADR-001 stands.**
- The pre-registered rule ("at least the baseline's hidden-test count with ≥ 30% fewer tokens") did not say which tokens. Measured by output tokens it would be met; measured by all tokens, or by what the plan actually consumes, the saving is 5–6%, far below 30%.
- The single agent writes less but re-reads a long single-session context, so its cached input almost cancels the saving.
- With equal hidden-test results, the quality signals favour the pipeline: fewer check failures, a clarifying question instead of a guess, and no debris left in the PR.

**Caveats, reported as threats to validity:**
- The rule's ambiguity.
- n = 5, one run each.
- The single variant's round-2 failure on #7 was partly an implementation defect: its prompt did not point it at the reviewer's findings, and the pipeline's implementer prompt did.
