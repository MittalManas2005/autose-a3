# ADR-013: Independent reviewer, revised: an approval needs evidence that the reviewer ran the tests

- **Status:** Accepted, amended by ADR-016 (2026-11-22: the maintainer's `/autose` answers are part of the issue for the spec and the reviewer)
- **Date:** 2026-11-22
- **Supersedes:** ADR-008
- **Assignment decision:** D8 (reviewer independence)
- **Decided by:** MittalManas2005, after smoke-test run 45003925819 (option prepared with AI assistance)

## Context
ADR-008 made the reviewer independent by structure: its own job, inputs, prompt, model, permissions and GitHub identity. Its verdict check was: "An approval must state what was verified."

The smoke-test run showed that this check is **satisfied by words alone**.

| Evidence | Source |
|---|---|
| The reviewer's **only** shell command was one chained call (`python -m unittest … \| tail -4; flake8 …; python -c …`). It was denied as a whole, because `tail` and bare `flake8` are not allowed. | `review` artifact, `logs/6-review-reviewer-1.json`, `permission_denials` |
| The reviewer then wrote: "I could not run the tests, flake8 or any probe inputs because Bash was denied in this environment, so this approval rests on reading the code only", and **approved**. The verdict passed validation because `verified` was not empty. | [PR #2 review](https://github.com/MittalManas2005/markdown/pull/2), run [45003925819](https://github.com/MittalManas2005/markdown/actions/runs/45003925819) |
| The identity design itself worked. The App opened PR #2, CI started on its own (13 passed, 1 skipped), and `github-actions[bot]` posted a real **APPROVED** review. | Same run |
| Claude Code records every tool call and its result in a session transcript (`~/.claude/projects/<cwd>/<session>.jsonl`), including denials and command output. The same call can appear twice. | Local inspection, Claude Code 2.1.319 |
| With one-command-per-call rules in the prompt, a local reviewer run on the same PR ran 7 distinct commands (full suite, TOC tests, flake8, 4 edge-case probes) with 0 denials. | Local run, 2026-11-22 |

The reviewer was honest, which is good. But ADR-007 says **code decides every check**, and here the check depended on the reviewer's own description of its work.

## Decision
Everything in ADR-008 still holds, with these changes:

**1. An approval requires executed evidence, checked by code.**
- After the reviewer finishes, the review job reads its **session transcript** and extracts every Bash call, de-duplicated by call ID. For each call it records whether it was denied, whether it failed, and the end of its output.
- `approve` is accepted only if the transcript contains a `python -m unittest` command that **the reviewer itself ran** and that passed (no error, no `FAILED (`).
- If not, the verdict is rejected. The PR gets a "review could not be completed" comment listing the commands that did run, and the run ends in state `review_error`. It does not count as an approval.
- `request_changes` does not need a test run. A defect found by reading, with file and line as evidence, is still valid.

**2. The posted review shows what was run.** The review includes "Commands I ran (from the session transcript, not self-reported)", with ok, failed or denied for each command.

**3. The reviewer can run what its checklist asks for.**
- The allowlist adds `python -m flake8 …` next to `python -m unittest …` and `python -c …`.
- The prompt lists the exact command forms and says to use one plain command per call.

**Unchanged from ADR-008:**
- **Separation:** own job on a fresh runner, with no build artifacts and no PR description.
- **Prompt:** own adversarial checklist.
- **Model:** Sonnet.
- **Permissions:** read and test only; no edits, git, `gh` or network.
- **Verdict rules:** a change request needs a target stage and findings with evidence.
- **Identities:** the GitHub App opens the PR; the review is posted as `github-actions[bot]`.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| Keep ADR-008: trust the reviewer's `verified` list | Shown insufficient by the smoke-test run: an approval with nothing executed passed. |
| Ask the reviewer to self-report `commands_run` in its JSON verdict | Better than nothing, but still self-reported. The transcript is the CLI's own record and costs nothing extra. |
| The review job runs the tests itself and attaches the results | CI already runs the suite (stage 5). The point is that the *reviewer* exercises the change with its own probes, and a deterministic re-run wouldn't show that. |
| Refuse any review whose commands were denied | Too strict. Denials are expected and harmless, and a reviewer that retries correctly should not be penalised. |

## Consequences
**Positive**
- "The reviewer verified the behaviour" becomes a fact checked by code, which closes the gap between ADR-007 and ADR-008.
- Reviews on GitHub show their own evidence, which helps a maintainer and the report.
- A reviewer that cannot run code now fails visibly (`review_error`) instead of silently approving.

**Negative / risks**
- Relies on Claude Code's transcript format, which is an internal file. If the format changes, approvals fail closed as `review_error`, not open. The format is covered by a unit test and should be re-checked on CLI upgrades.
- A reviewer could run the suite and still approve a weak change. Running tests is necessary, not sufficient. This is what the seeded-PR experiment measures.
- Slightly more reviewer turns and tokens, because it actually runs the commands.

## Evaluation
