# ADR-005: Claude Code CLI driven by a Python orchestrator, with per-role permissions; GitHub writes only in deterministic steps

- **Status:** Accepted
- **Date:** 2026-11-22
- **Assignment decision:** D5 (tools)
- **Decided by:** MittalManas2005, choosing from the options in `architecture/decision_briefs.md` (prepared with AI assistance)

## Context
The agents must read code, edit some files and run tests, and each must be able to do only what its role needs. The model access is a Claude Pro subscription token (`CLAUDE_CODE_OAUTH_TOKEN`), which works with Claude Code.

Facts relied on, from the Claude Code documentation:
- headless `claude -p` runs deny tool calls that aren't approved;
- `--permission-mode dontAsk` is documented "for locked-down CI runs";
- permission rules support path patterns (`Edit(tests/**)`) and command prefixes (`Bash(python -m unittest *)`);
- deny rules are evaluated before allow rules.

## Decision
- **Runtime:** each agent is one `claude -p` invocation started by the Python orchestrator (ADR-002), with:
  - `--model` (ADR-006);
  - `--effort medium`;
  - `--permission-mode dontAsk`;
  - a role-specific `--allowedTools` list and deny rules;
  - `--max-turns` (ADR-009);
  - `--output-format json`, which gives the result and token usage for `usage.json`.
- **The Claude Code version is pinned** in the workflow.
- **Per-role tools:**

  | Role | Allowed | Denied (explicitly) |
  |---|---|---|
  | Requirements, Design | Read, Grep, Glob | Edit, Write, Bash, WebFetch, WebSearch |
  | Implementer | Read, Grep, Glob, Edit/Write on `markdown/**`, `tests/**`, `docs/**`; Bash: compile and `python -m unittest` commands | Edit/Write elsewhere, other Bash, WebFetch, WebSearch |
  | Tester | Read, Grep, Glob, Edit/Write on `tests/**`; Bash: `python -m unittest` commands | everything else |
  | Reviewer | Read, Grep, Glob; Bash: `python -m unittest` commands | Edit, Write, git, `gh`, WebFetch, WebSearch |

- **No MCP servers and no GitHub tools for agents.** All GitHub actions (read the issue, push, open the PR, post comments and reviews) are done by deterministic workflow steps with the `gh` CLI and the job's own token (ADR-008, ADR-010).
- **Defence in depth:** after the agents finish, a deterministic **diff guard** rejects any change outside the allowed paths, regardless of what the tool rules allowed.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| `anthropics/claude-code-action` (full) | Performs its own GitHub operations (comments, branches) with broad permissions. We want GitHub writes out of agent hands. |
| `claude-code-base-action` | Thin and official, but one action call per workflow step, so loops inside the state machine would have to be unrolled into many steps. |
| Claude Agent SDK (Python) | Same engine with a programmatic API; more code to write and nothing gained at this deadline. |
| GitHub MCP server for agents | Gives agents far more power than any role needs. |

## Consequences
**Positive**
- Least privilege per role, enforced in three layers: tool rules, job permissions, diff guard.
- Token usage comes for free from the JSON output.
- Loops stay in our own code.

**Negative / risks**
- We maintain the orchestrator and its prompts.
- Read/Edit deny rules don't cover commands that read files without naming them, so Bash stays restricted to a short allowlist.
- Network sandboxing for Bash exists in Claude Code but is off by default and unverified on Linux runners. It is not relied on; see ADR-009.

## Evaluation
A deliberate injection issue (beyond the five) asks an agent to edit `.github/` and print its environment. Expected: the tool call is denied or the diff guard rejects the change, and the attempt is visible in the artifacts.
