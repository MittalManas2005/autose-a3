# ADR-014: Review runs execute only trusted AutoSE code, and only on PRs from the fork's own branches

- **Status:** Accepted
- **Date:** 2026-11-22
- **Amends:** ADR-010 (authorization for review-only runs). ADR-010 otherwise stays in force.
- **Assignment decision:** D9 (safety) and D10 (triggers)
- **Decided by:** MittalManas2005 (option prepared with AI assistance)

## Context
This was found by inspection while preparing a review-only re-check of PR #2 after ADR-012 and ADR-013. No run failed because of it.

**How the review job worked:**
- It checked out the PR head (`refs/pull/<n>/head`) and then ran `python -m autose.review` in that checkout.
- Python puts the current directory first on the import path, so **AutoSE's own orchestration code was imported from the branch under review.**

**Two consequences:**

| Problem | Concrete case |
|---|---|
| **Stale code.** A PR branch created before an AutoSE change runs the old reviewer. | PR #2 was created from `38c9930`. A `/autose` re-check would have run the reviewer *without* the ADR-013 evidence rule, so it would have tested nothing new. |
| **Untrusted code with secrets.** A PR from another fork can change `autose/review.py`. If a maintainer comments `/autose` on it, that code runs in a job holding a `pull-requests: write` token and the Claude token. It is the classic `pull_request_target` mistake, made in a different way. The same applies to packaging files that `pip install -e .` executes. | Any outside contributor's PR. ADR-010 checks *who comments*, not *whose code runs*. |

**Verified locally:**
- A checkout containing a planted `autose/__init__.py` is imported by `python -m autose.review`.
- With `python -P` (Python 3.11+, "don't prepend the current directory") and `PYTHONPATH` pointing at a trusted copy, the trusted copy is imported.

**Two details in ADR-010 differ from the implementation:**
- Unauthorized triggers are ignored silently (the reason is in the gate log), not answered with a reply.
- The concurrency group is `autose-<number>`, not `autose-issue-<number>`. Issue and PR numbers share one namespace on GitHub, so this is equivalent.

## Decision
**1. AutoSE's code always comes from the trusted base commit.**
- The review job checks out the PR head (the code to review) and, separately, a sparse checkout of `autose/` at the run's base commit. For a review-only run that is the default branch at trigger time; for a full run it is the base the build used.
- It moves the trusted copy outside the reviewed tree (`$RUNNER_TEMP`) and runs `PYTHONPATH=<trusted> python -P -m autose.review`.
- Prompts, the skill, the verdict rules and the GitHub posting logic therefore always come from `main`. The PR's code is only reviewed and tested, by the reviewer agent, whose commands get no credentials (ADR-012).
- The build and release jobs already ran trusted code: round 1 checks out the base commit, and later rounds check out the bot's own branch, where the diff guard forbids changes to `autose/**`.

**2. Review-only runs are allowed only on PRs whose head branch is in the fork itself.**
- The gate looks up `head.repo.full_name` through the API and refuses review-only runs, both `/autose` comments and `workflow_dispatch`, when it differs from the repository.
- Only maintainers and the AutoSE App can push branches to the fork, so every reviewable PR was pushed by a trusted identity. Seeded reviewer-check PRs are created as fork branches, so they qualify.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| Keep running from the PR head and document it | Fails both ways: stale reviewers make experiments inconsistent, and outside PRs become code execution with secrets. |
| Delete the PR's `autose/` directory before running | Fixes the stale-code case, but `pip install -e .` and other files in the PR could still tamper with the job's Python environment. It also hides part of the repository from the reviewer. |
| Move AutoSE's code into a separate repository | Clean separation, but needs a cross-repository token or a public package. The bundled copy in the fork is already established (ADR-003). |
| Allow outside PRs and run the review in a job without secrets | The reviewer needs the Claude token, and posting the review needs a write token. Splitting this further is possible, but no AutoSE use case requires reviewing outside forks. |

## Consequences
**Positive**
- Every review, including the E2 and seeded-PR experiment runs, uses the same current reviewer code whatever the PR's base. That makes the experiments consistent.
- Code from outside the trusted identities never runs in a job that holds secrets.

**Negative / risks**
- AutoSE cannot review PRs from other people's forks. For this assignment that is intended. A real deployment would need a separate, secret-free review design for those.
- `pip install -e .` still installs the PR's package in the review job, in a step without secrets. For fork branches that is acceptable because only trusted identities can create them. The diff guard also stops the bot from changing packaging files.

## Evaluation
- **Re-check of PR #2:** a `/autose` comment on PR #2 must produce a review that lists the commands the reviewer ran (ADR-013). That can only happen if the trusted `main` code ran, not the PR branch's older code.
- **Unit tests:** cover the gate refusing PRs from other forks, for both comment and dispatch triggers.
