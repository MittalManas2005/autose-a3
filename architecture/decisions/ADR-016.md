# ADR-016: The maintainer's answers are part of the issue, for the spec and for the reviewer

- **Status:** Accepted
- **Date:** 2026-11-22
- **Amends:** ADR-003 and ADR-013 (what the reviewer receives); ADR-011 (update mode of stage 1). Both stay in force otherwise.
- **Assignment decision:** D3 (hand-offs) and D8 (reviewer)
- **Decided by:** MittalManas2005, after baseline run 45010344467 (option prepared with AI assistance)

## Context
Issue #7 is the vague evaluation issue. Its flow worked as designed:
1. Stage 1 asked a clarifying question (run 45008937436).
2. The maintainer posted the scripted answer as an `/autose` comment, naming three link forms.
3. The run resumed (run 45010344467) and ended with an approved PR, #12.

The hidden tests then failed 1 of 4: `` [text][`x`] ``, a code span in the *reference ID*, still does not link. The cause was traced through the artifacts (`results/evidence/45010344467/`):

| Stage | What happened |
|---|---|
| 1 Requirements (update mode) | The spec covered `` [`code`] `` and `` [`code`][ref] ``, but **not** the third form the answer named, `` [text][`foo`] ``. |
| 2–4 | Faithful to the incomplete spec. Every check passed. |
| 6 Reviewer | Approved, as did the Haiku re-review in E2. **It received only the issue body**, which says "links with code in them don't work sometimes". Judged against that text, the PR is correct. |

**Two independent gaps:**
1. Nothing made stage 1 account for *every* example in an answer.
2. ADR-003 and ADR-013 defined the reviewer's input as "the issue", implemented as the issue **body**. The maintainer's clarification lives in a **comment**, so the reviewer judged against stale requirements. That is an information gap, not a judgement failure: neither Sonnet nor Haiku could have caught it.

The E1 single agent missed the same form after guessing, without asking (run 45011722169).

## Decision
**1. The reviewer receives the maintainer's answers.**
- The review job appends to `.autose_review/issue.md` the text of every issue comment that the gate would accept as an answer: it starts with `/autose`, is from a person rather than a bot, comes from an `OWNER`, `MEMBER` or `COLLABORATOR` with write access, and has text after the command.
- The answers are wrapped in `<untrusted_answers>` markers, and the reviewer prompt treats them as part of the requirements.
- Nothing written by the pipeline is included: no bot status comments, no spec, no design, no test report. **The independence boundary of ADR-013 is unchanged.** The reviewer still sees only what a human wrote about the problem, plus the diff and the code.

**2. In update mode, stage 1 must cover every example in the answers.**
- The requirements prompt, and the single agent's, now require at least one acceptance criterion per concrete example or case in the maintainer's answers, using the same input form. The spec's change log must list each example and the criterion that covers it.
- This is a prompt rule, not a code check. Matching examples to criteria mechanically fails on harmless renaming (the agent writes `` [`code`] `` for the answer's `` [`foo`] ``). The reviewer change above is the deterministic safety net.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| Give the reviewer the whole issue thread | It would include the bot's status comments, which quote the agent's question and the run state: implementer-side content that ADR-013 keeps out. |
| Give the reviewer the spec | The spec is the implementer's interpretation. Reviewing against it is exactly how a reviewer ends up agreeing with the implementer, so it was rejected in ADR-003 and stays rejected. |
| Mechanically match answer examples to ACs | Brittle across renaming. False failures would stop good runs at stage 1, which has no retry. |
| Only one of the two fixes | Each fix alone leaves a single point of failure: stage 1 can still drop an example, and the reviewer can still miss it. Together they give two independent chances to catch the miss. |

## Consequences
**Positive**
- The reviewer judges against the requirements the maintainer actually stated.
- Answers get double coverage: once at the spec, once at review.

**Negative / risks**
- More untrusted text reaches the reviewer, in maintainer comments. It is marked untrusted, it comes only from write-access users, and the reviewer has no write tools.
- The prompt rule can still be ignored by the model. The reviewer change is what makes the outcome checkable.

## Evaluation
- **Re-run of #7** with this ADR in force, as "after the fix" evidence. Measures: does the spec cover all three forms, do the hidden tests pass 4/4, and if not, does the reviewer now request changes?
- **Unit tests** cover which comments count as answers: bare triggers, bot comments, outsiders and collaborators without write access are all excluded.
