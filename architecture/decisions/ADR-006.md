# ADR-006: Haiku for the producing roles, Sonnet for the reviewer, medium effort

- **Status:** Accepted
- **Date:** 2026-11-22
- **Assignment decision:** D6 (models)
- **Decided by:** MittalManas2005, choosing from the options in `architecture/decision_briefs.md` (prepared with AI assistance)

## Context
The project runs on a Claude Pro subscription. All agents share its usage limits, so cost and speed matter. Available models: Claude Haiku (fast, cheapest) and Claude Sonnet (more capable).

The reviewer must not simply agree with the implementer. Anthropic's harness study found that out of the box "Claude is a poor QA agent" that talks itself out of real issues. It also found that tuning a standalone evaluator to be sceptical is "far more tractable" than making a generator self-critical.

## Decision
- **Requirements, Design, Implementer, Tester** (and the single agent in experiment E1): **Claude Haiku**, effort `medium`.
- **Reviewer: Claude Sonnet**, effort `medium`.
- Models and effort are set per role in one configuration file, so experiment variants can change them without code changes. The model names used in each run are logged in `usage.json`.

**Rationale:**
- The producing roles run most often, including retry loops, so a cheap, fast model keeps runs within the Pro plan's limits.
- The reviewer runs once per round and is the last line of defence, so the more capable model goes where catching mistakes matters most.
- A stronger, *different* model reviewing a weaker model's work also reduces shared blind spots.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| Sonnet for all roles | Probably better code, but several times the usage per run, and no model diversity between implementer and reviewer. |
| Haiku for all roles, including the reviewer | Cheapest, but the reviewer would share the implementer's blind spots. This is **experiment E2's variant**, so the choice is tested. |
| Sonnet for producing roles, Haiku reviewer | Spends capability on generation but weakens the independent check. |

## Consequences
**Positive**
- Low usage per run.
- Capability is concentrated in the reviewer.
- Implementer and reviewer use different models.

**Negative / risks**
- Haiku may follow the long A1 skill less faithfully, or need more retries. Retries are budgeted (ADR-009), and failures show up in stage pass rates.
- Results apply to these model versions only. This is a threat to validity, stated in the report.

## Evaluation
**Experiment E2:** Sonnet vs Haiku reviewer on the same pull requests (the 5 seeded reviewer-check PRs and the real PRs). Measured: defects caught, false approvals, false requests for changes, tokens.

If Haiku catches as much at lower cost, this ADR is superseded.
