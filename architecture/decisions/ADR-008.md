# ADR-008: Independent reviewer: own job, prompt, model, permissions and GitHub identity

- **Status:** Accepted
- **Date:** 2026-11-22
- **Assignment decision:** D8 (reviewer independence)
- **Decided by:** MittalManas2005, choosing from the options in `architecture/decision_briefs.md` (prepared with AI assistance)

## Context
Assignment rules for the reviewer:
- it may see only the issue, the diff and the repository at the PR's latest commit;
- it may run code but not push;
- it must not see the implementer's conversation or reasoning;
- it must not simply agree with the implementer.

GitHub rules that affect the design:
- a PR's author cannot approve or request changes on their own PR;
- PRs opened with `GITHUB_TOKEN` get CI runs in an approval-required state;
- events created with `GITHUB_TOKEN` don't start other workflows.

## Decision
**Separation, enforced by the system rather than by instructions alone:**
- **Own job** on a fresh runner. It downloads no build artifacts and doesn't read the PR description (ADR-003).
- **Own prompt**, with an adversarial checklist:
  - derive the expected behaviour from the issue alone;
  - run the test suite and the new tests;
  - probe edge cases with its own inputs;
  - check that no tests were weakened or deleted;
  - check scope creep and repository rules (e.g. the changelog entry).
- **Own model:** Sonnet, while the producing roles use Haiku (ADR-006).
- **Own permissions:** read, search and test commands only. No edits, no git, no `gh`, no network tools (ADR-005).
- **Evidence-required verdict:** `verdict.json` with `approve` or `request_changes`. A change request must name the target stage and list findings, each with evidence (file and line, failing input, or test output). An approval must state what was verified.

**Own identity:**
- The **Release job opens the PR as a GitHub App** (installation token, 1-hour lifetime, permissions `contents: write`, `pull-requests: write`).
- The **review is posted as `github-actions[bot]`** with the job's `GITHUB_TOKEN`. Because these are different identities, the reviewer can post real `APPROVE` / `REQUEST_CHANGES` reviews.
- This needs the fork setting "Allow GitHub Actions to create and approve pull requests". PRs opened by the App also trigger upstream CI normally (ADR-010).

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| Everything via `GITHUB_TOKEN`, review as a comment plus a label | No setup, but no formal approval, and CI on bot PRs waits for approval unless upstream's CI file is modified. |
| A personal access token opens the PR | Bot actions would appear as the human maintainer, blurring who did what; long-lived credential. |
| Reviewer in the same job as the implementer | It would share the filesystem and could read every artifact; independence would depend on instructions only. |
| Debate panel of several reviewers | Probably stronger, but 3–4× the reviewer cost. A possible future experiment. |

## Consequences
**Positive**
- Independence is structural: separate runner, separate inputs, separate model, separate permissions, separate identity.
- Formal GitHub reviews are visible on the PR.

**Negative / risks**
- One-time setup of a GitHub App (create, install on the fork, store app ID and private key as secrets).
- A bot approval could satisfy a "1 approval required" rule. Branch protection is configured so the merge is still a human action.
- The reviewer can read agent prompts in the repository (ADR-003). The reviewer may also be wrong; this is measured.

## Evaluation
**Experiment E2** (Sonnet vs Haiku reviewer) on 5 seeded reviewer-check PRs, each with ground-truth labels (one correct change, four with known defects), plus the real PRs. Measured:
- defects caught;
- false approvals ("approves everything");
- false requests for changes;
- tokens.
