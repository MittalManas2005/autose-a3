# ADR-002: Deterministic state machine with review rounds unrolled in the workflow

- **Status:** Accepted
- **Date:** 2026-11-22
- **Assignment decision:** D2 (control flow)
- **Decided by:** MittalManas2005, choosing from the options in `architecture/decision_briefs.md` (prepared with AI assistance)

## Context
The stages need backward transitions with bounds:
- failing tests return to implementation;
- repeatedly failing tests return to design;
- review findings return to design or implementation, at most twice.

GitHub Actions jobs form a directed acyclic graph and cannot loop. Different parts of the run need different permissions: building has no GitHub write access, release needs push and PR rights, review must be isolated. Control flow must also be auditable after the fact.

## Decision
- **Stages 1–4 run inside one read-only `build` job,** driven by a deterministic Python **state machine** (the orchestrator). It invokes the agents, runs the checks (ADR-007) and applies a fixed transition table with budgets (ADR-009):

  | From | Condition | To | Budget |
  |---|---|---|---|
  | 1 Requirements | PASS | 2 | — |
  | 1 Requirements | NEEDS_INPUT / FAIL | stop | — |
  | 2 Design | check passes | 3 | 1 retry with validator findings |
  | 3 Implementation | check passes | 4 | shares stage 4's budget |
  | 4 Testing | suite fails | 3 | 2 times |
  | 4 Testing | still failing after stage-3 retries | 2 | once |
  | 4 Testing | passes | release | — |

- **Release and Review are separate jobs** with their own permissions (ADR-005, ADR-008).
- **Review rounds are unrolled in the workflow graph:** build → release → review for round 1, then conditional rounds 2 and 3, implemented as one reusable workflow called three times. A later round runs only if the previous review returned `request_changes`. It starts at the stage the reviewer named, which the orchestrator checks is allowed (`design` or `implementation`).
- **"At most twice"** is read literally: at most **two send-backs**, so at most three reviews. The bound is guaranteed by the graph itself, not only by a counter.
- **Who decides to go back: code.** Agents report results (failing tests, verdicts); the state machine decides.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| Everything in one job | Loops are easy, but one permission set covers everything and the reviewer would share a filesystem with the implementer. |
| One Actions job per stage | Per-stage permissions and a clear graph, but jobs can't loop, so retries would need copy-pasted jobs per attempt. |
| Workflows dispatching each other | Unlimited loops, but state must cross runs and a single run is harder to follow. |
| LLM planner chooses the next stage | Non-deterministic control flow that can skip checks or loop; harder to bound and to audit. |

## Consequences
**Positive**
- Loops exist where they're needed, permission boundaries where they matter.
- Bounds are explicit and testable.
- Every transition is logged in `run_state.json`.
- The Actions graph shows each review round.

**Negative / risks**
- The workflow file is long (mitigated by a reusable round workflow).
- A full worst-case run is long: 3 builds, releases and reviews. Job timeouts are set (ADR-009).
- The transition table is fixed, so unusual situations stop the run instead of improvising.

## Evaluation
For every run, `run_state.json` records the transitions taken, the retries used and the stop reason. `results/results.csv` reports how often each loop fired and that no budget was exceeded.
