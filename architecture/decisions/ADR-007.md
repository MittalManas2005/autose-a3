# ADR-007: Deterministic checks make every pass/fail decision; LLM output is only input

- **Status:** Accepted
- **Date:** 2026-11-22
- **Assignment decision:** D7 (checks)
- **Decided by:** MittalManas2005, choosing from the options in `architecture/decision_briefs.md` (prepared with AI assistance)

## Context
Every stage has a required check, and a stage may hand over only when its check passes. An LLM's own claim that its work is finished is not reliable. The course catalogue's generator–critic demo shows "a passing critique does not guarantee passing tests".

The target repository has strong executable signals:
- a 1,166-test `unittest` suite;
- flake8;
- upstream CI, including a changelog-entry check.

## Decision
The orchestrator's checks are code. Each check writes its result and reasons into the stage artifact, and the state machine acts on that result (ADR-002).

| Stage | Deterministic check | LLM involvement |
|---|---|---|
| 1 | Parse `spec.md` front matter; `status == PASS`; every AC has an ID, a concrete input, a public call and a known oracle kind; every FR has an AC | The A1 skill's own validation (V1–V6, stage gate) produces `status`, and code verifies the structure behind it |
| 2 | Parse `design.md`; every listed file exists or is marked new; every listed function or class exists in that file (Python `ast`) or is marked new; discrepancy section present | — |
| 3 | Diff non-empty; diff guard (allowed paths, no deleted test files or test methods); `pip install -e .`; `python -m compileall markdown`; import and convert smoke test; `flake8 markdown tests` | — |
| 4 | Every AC ID appears in ≥ 1 new test; new tests **fail on the base commit** for non-preservation ACs (no empty tests); `python -m unittest discover tests` passes in a clean environment; test count not lower than base, measured in the same environment | The Tester writes the tests; code runs them |
| 5 | PR open (API); every CI check run on the head commit concludes `success` within the timeout | — |
| 6 | Reviewer's `verdict.json` parses against a schema; `request_changes` must name a stage and give findings with evidence | The Reviewer's judgement is the verdict; code enforces the format and the round limit |

Final pass/fail is made by code. The only exception is the merge, which is the human's decision.

## Alternatives considered
| Alternative | Why not chosen |
|---|---|
| LLM judge for each stage | Cheap to build, but non-deterministic and prone to approving its own kind. Used only where judgement is the point (stage 1 content, stage 6 verdict). |
| Tests only, no structural checks on spec and design | Bad specs and designs would surface late as failing code, wasting retries. |
| Rely on upstream CI alone | CI doesn't check acceptance-criteria coverage or whether new tests actually exercise the change. |

## Consequences
**Positive**
- Checks are reproducible and explainable.
- Stage pass rates mean something.
- The "fails on base" check catches vacuous tests.

**Negative / risks**
- Structural checks can pass a well-formed but wrong spec or design. Hidden tests and the reviewer measure what they miss.
- Test counts depend on the environment (with Pygments installed, 60 more tests are skipped), so counts are compared only within one job's environment.

## Evaluation
`results/results.csv` records each check's result per stage per run. The report compares check verdicts with hidden-test outcomes, i.e. where the checks passed work that hidden tests or the reviewer rejected.
